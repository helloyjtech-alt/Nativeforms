

PRODUCT REQUIREMENTS DOCUMENT

Theme Editor Experience

Custom Form Builder — Shopify App

Version 1.0  ·  Block Schema, Sidebar Settings, Field Types, Styling, Templates & Interactions





1.  Purpose & Scope

This PRD defines the complete Shopify Theme Editor experience for the Custom Form Builder app. The Theme Editor is the ONLY place where merchants create forms, add fields, configure field behaviour, and style the form. The Admin Dashboard (covered in a separate PRD) handles post-creation management: viewing submissions, billing, and notifications.



What this PRD covers:

The Form Block schema — how the block is registered and what Shopify natively renders in the sidebar

Every sidebar setting exposed on the Form Block (root level)

Every child Field Block type and each field's sidebar settings

The design-mode overlay UI injected by the app's JS (template gallery, field picker, in-canvas controls)

Styling settings at global (form) level and per-field override level (referencing the Design & Styling PRD for property details)

The template system — browsing, applying, and managing templates

Multi-step form configuration

Conditional logic (Growth plan)

How the Theme Editor experience connects back to the Admin Dashboard and App Backend

Plan-gated feature locks inside the Theme Editor



Out of scope: Form styling property detail (covered in Form Design & Styling PRD v1.0). Admin Dashboard pages (covered in Admin Dashboard PRD v1.0). Storefront runtime rendering and submission handling (covered in Backend Architecture doc).



2.  Architecture Overview — How the App Lives in the Theme Editor

The Custom Form Builder is a Shopify Theme App Extension. It ships two things into the merchant's theme:



2.1  The Form Block (App Block)

A single root App Block registered as blocks/custom-form-builder.liquid in the extension package. Merchants add this block once per form — to any section that supports app blocks (most built-in sections do, e.g. "Image with text", "Rich text", any custom section). Each instance of the block = one independent form.

Block type identifier: custom-form-builder (referenced in schema as app blocks)

Maximum 1 instance per section template (configurable in the extension schema to allow multiple)

The block's Liquid renders only a lightweight container div with a data-fbw-form-id attribute; all real rendering is done by the Form Runtime JS, which hydrates the form from the block's settings JSON



2.2  Nested Child Blocks (Field Blocks)

Each field in the form is a separate child block nested inside the Form Block. Shopify natively supports nested blocks in theme extensions. The Form Block's schema defines a blocks array that whitelists only this app's own field block types — no other app's blocks can appear here, and the Form Block itself cannot nest another Form Block.

Each field block type is a separate Liquid file: blocks/field-text.liquid, blocks/field-email.liquid, etc.

Merchants add, remove, and reorder field blocks using Shopify's native "Add block" button and drag handles in the Theme Editor — no custom UI is required for this

The ordering of child blocks in the Theme Editor is the rendering order of fields in the form



2.3  Design-Mode Overlay (App-Injected JS)

The Theme Editor loads the form's preview in an iframe. When Shopify signals design mode (window.Shopify.designMode === true), the app's JS activates an overlay layer on top of the live canvas. This overlay provides the enriched creation experience: the template gallery modal, the visual field picker, in-canvas drag handles, and contextual tooltips. This overlay is ONLY visible inside the Theme Editor — it is never shown to customers on the live storefront.

5.  Design-Mode Overlay — App-Injected UI

When the Theme Editor loads, the app's design-mode JS detects window.Shopify.designMode === true and activates the overlay layer on top of the live canvas. This is NOT a custom sidebar — it is injected into the canvas iframe. The overlay is always hidden on the live storefront.



5.1  Empty-State Overlay (First Block Add)

When a Form Block is added to a section for the first time (no child field blocks yet), the canvas shows the block's empty-state overlay instead of a form. This replaces what would otherwise be a blank white box.



Element

Details

App logo + block name

"Custom Form Builder" shown prominently inside the empty canvas area.

Two primary action buttons

"Browse Templates" (primary, filled) and "Start Blank" (secondary, outlined).

Keyboard shortcut hint

Small text: "Or use the sidebar to add individual fields."

Animated dashed border

The empty-state has an animated dashed border to signal it is interactive.

Clicking "Browse Templates"

Opens the Template Gallery Modal (Section 5.2).

Clicking "Start Blank"

Dismisses the overlay. Sidebar shows a focused tooltip pointing at the native "Add block" control with hint text: "Click Add block to add your first field."



5.2  Template Gallery Modal

A full-screen modal overlaid inside the canvas iframe. Fetched lazily (JS lazy-loads the modal HTML/CSS bundle on demand). Data loaded via signed App Proxy: GET /apps/formbuilder/templates.



Element

Details

Header

Modal title: "Choose a Template." Close button (X) top-right. A back arrow if inside a category drill-down.

Search box

Real-time filter on template name and tags. Debounced 300ms. Shows matching count.

Category filter chips

All / Contact / Feedback / Survey / Registration / Order / Application / Legal / Custom. Selecting a chip filters the grid.

Template cards grid

3-column grid on desktop, 1 on mobile. Each card: thumbnail screenshot, template name, field count badge, short description. Hover state reveals a "Preview" button.

"Preview" button on hover

Opens a full-size preview of the template rendered in an inner preview pane (same canvas, populated with placeholder data). Preview has a "Use this template" CTA and a back arrow.

"Use this template" CTA

Triggers: POST /apps/formbuilder/templates/:key/apply via App Proxy. Backend clones template fields into DB. Backend calls Shopify Admin GraphQL (themeFilesUpsert) to write the nested Field blocks. Theme Editor refreshes — merchant now sees real individual field blocks.

Plan-gate overlay on templates

Growth-only templates (e.g. multi-step with rating + signature) show a lock icon overlay on their card. Hovering shows "Requires Growth plan." Clicking opens the upgrade prompt (links to Admin Billing page).

Empty search state

"No templates match your search." + "Clear search" link.

7.  Conditional Logic (Growth Plan)

Plan gate: Growth only. On Free and Starter, the Conditional Logic section is visible in the sidebar but all controls are locked. An inline upsell card reads: "Conditional logic is available on the Growth plan. Show or hide fields based on what your customers select." with a link to the Billing page.



7.1  What Conditional Logic Does

Conditional logic (also called "show/hide rules" or "branching logic") allows specific fields to be shown or hidden based on the values a customer has entered in earlier fields. This enables dynamic forms that adapt to the customer without requiring multiple separate forms.

Example: Show a "File Upload" field ONLY if the customer selects "Yes" in a Radio Group asking "Do you have supporting documents?"

Example: Show a "Company Name" text field ONLY if the customer's "Account Type" dropdown is set to "Business"

Example: Skip an entire step in a multi-step form if the customer selects a specific value



7.2  Conditional Logic Sidebar — Per Field

Each field block has a "Conditional Logic" section at the bottom of its sidebar settings (below the styling section). It contains:

Setting / Element

Description & Behaviour

Plan Gate

Logic Mode toggle

Enable / Disable conditional logic for this field. When disabled (default), the field always shows. When enabled, the rules below determine visibility.

Growth

Visibility default

What this field does when no rules match or when a referenced field hasn't been filled yet: Show by default / Hide by default.

Growth

Rule set (AND/OR)

A top-level operator: "Show this field when ALL of the following are true (AND)" or "Show this field when ANY of the following are true (OR)".

Growth

Each rule is a row: [Field selector dropdown] [Condition dropdown] [Value input]. Up to 10 rules per field.

Growth

A dropdown listing all other fields on the same form (by their Label). Fields listed before the current field in form order are available as source fields.

7.3  Conditional Logic — Multi-Step Interaction

When multi-step mode is enabled alongside conditional logic:

A hidden field does not count toward step validation — if a hidden required field exists in the current step, it does not block the "Next" button

If ALL fields in a step are hidden by conditional logic, that step is automatically skipped in the navigation sequence (the progress bar jumps to the next step with visible fields)

Step-skipping is re-evaluated on every value change, in real-time

Each template stored on the App Backend contains:

8.3  Template Application Flow

When a merchant selects "Use this template":

Step 1 — App Backend receives POST /apps/formbuilder/templates/:key/apply with the shop's access token (signed via App Proxy)

Step 2 — Backend looks up the template definition, creates a new Form DB record and one FormField DB record per template field

Step 3 — Backend builds the Shopify block schema JSON representing the Form Block with all child Field blocks embedded as nested blocks with their settings populated from the template field definitions

Step 4 — Backend calls Shopify Admin GraphQL themeFilesUpsert to write this block JSON into the current published theme's JSON template file

Step 5 — Theme Editor auto-refreshes the canvas (Shopify fires a postMessage to the iframe on theme file change)

Step 6 — Merchant sees their form populated with all template fields, individually editable as native child blocks

Step 7 — A success banner appears in the canvas overlay: "Template applied! Customize your fields in the sidebar."

10.  Form Publishing, Save & Sync



10.1  How Saving Works

The Theme Editor's native Save/Publish button is the ONLY save mechanism for form configuration. There is no separate save button in the sidebar or canvas overlay. The app does not intercept or duplicate Shopify's save flow.

When the merchant clicks Shopify's Save button: Shopify writes the entire theme JSON (including all block settings) to the published theme

The form's field configuration and visual settings are stored entirely inside the theme's JSON template file as part of the block schema — not in the app's database

The app's database (Form and FormField records) is the source of truth for submission routing, notification rules, and integration configuration, NOT for visual settings

On every Theme Editor load, the app's design-mode JS reads the current block settings from Shopify's block data object and syncs any changes back to the App Backend via a lightweight sync call — this keeps the DB in sync with the theme



10.2  Draft vs. Active Status

A form's status (Active / Draft / Archived) is managed in the Admin Dashboard and stored in the App Backend DB. The Theme Editor does not directly control this status — it is shown as a read-only badge in the Form Identity group (Section 3.1).

A new form block added to the theme starts as "Draft" in the DB until the theme is saved (published)

Once the theme is saved and the block is live, the form status transitions to "Active" automatically via a webhook (theme/publish webhook or a sync on next load)

Archiving or deleting a form is done in the Admin Dashboard — it does NOT remove the block from the theme. The block remains in the theme but the storefront runtime JS detects the "Archived" status and renders nothing (or a configurable replacement message)



10.3  Multiple Forms on the Same Page

Multiple Form Blocks can be added to the same page template (each in a separate section, or within sections that support multiple app blocks). Each block instance is independent:

Each has its own unique Form ID

Each has its own submission routing, notification settings, and Admin Dashboard entry

Styling is scoped per form block using the block's unique ID as a CSS scope

Multiple form submissions on the same page do not interfere with each other's success messages





11.  Client-Side Validation — Behaviour Specification

All validation runs in the browser before the form is submitted to the backend. The backend also validates (never trust the client), but the client-side validation provides immediate feedback.



11.1  Validation Trigger Modes

12.  Field Ordering, Duplication & Deletion



12.1  Reordering Fields

Field ordering is controlled entirely by Shopify's native Theme Editor drag-and-drop mechanism. The app does not implement a custom drag system.

Each child block has a native drag handle in the sidebar block list and in the canvas

The order of child blocks in the Shopify block JSON is the rendering order of fields in the storefront form

The app's backend syncs field order from the block JSON on every save



12.2  Duplicating Fields

A "Duplicate" button appears in the in-canvas hover toolbar (Section 5.4) and in the sidebar's three-dot menu for each field block.

Duplication creates a copy of the field block with all settings preserved

The duplicated field's Label gets " (copy)" appended

The duplicated field's Field Name/ID is suffixed with "_2" (or next available integer suffix) to avoid key collisions

The duplicate is inserted immediately after the original in the block order

If conditional logic rules reference the original field's ID, those rules are NOT copied to the duplicate — a warning toast notes: "Conditional logic rules referencing this field's ID were not duplicated. Update rules manually."



12.3  Deleting Fields

Fields are deleted using Shopify's native block delete button (the trash icon in the sidebar block list) or the in-canvas delete button (Section 5.4).

Deleting a field block removes it from the Theme Editor block list and from the live preview immediately

The field is permanently removed from the form on the next Theme Editor Save

If other fields have conditional logic rules that reference the deleted field, those rules become invalid — a warning banner appears in the sidebar: "One or more conditional logic rules reference a deleted field. Review rules on affected fields." with a list of affected field names.

Submissions already received that contained this field's data are not affected — the data is stored and remains visible in the Admin Dashboard Submissions inbox under the original field name

14.  Implementation Notes



14.1  App Block Registration

The Form Block is registered in extensions/custom-form-builder/blocks/form.liquid

The block schema lists all root-level settings and a blocks array that whitelists the app's own field block types by their block type strings (e.g. "@app/field-text", "@app/field-email", etc.)

The presets array registers a default preset so merchants see the block with a sensible default name in the "Add block" list

The limit setting on the parent section controls how many Form Blocks can be added per page section; this is set by the theme, not the app



14.2  Design-Mode JS Bundle

The design-mode JS bundle is loaded via a <script> tag in the block's Liquid file, guarded by an if Shopify.designMode check

The bundle is lazy-loaded — the main block JS (Form Runtime, ~12KB gzipped) loads on all pages; the design-mode overlay bundle (~40KB gzipped) loads only when designMode is true

The overlay communicates with the App Backend via the signed App Proxy endpoint to avoid exposing the backend URL to the browser

postMessage is used to communicate between the Theme Editor parent frame and the preview iframe when reflecting design-mode state changes



14.3  CSS Architecture

All theme block settings write to CSS custom properties (--fbw-*) on the block root element (#fbw-{blockId})

The Form Runtime JS generates a <style> block scoped to the form block ID and injects it into the <head> on page load

State-specific CSS (hover, focus, error) is written to pseudo-class and data-attribute selectors within the same scoped style block

Responsive styles use @media (max-width: 768px) breakpoints injected in the same scoped style block

Dark mode uses @media (prefers-color-scheme: dark) or a [data-color-scheme="dark"] data attribute on the block root, matching the theme's dark mode implementation



14.4  App Proxy — Signed Requests

All JS-initiated requests from the Theme Editor canvas iframe to the App Backend go through the Shopify App Proxy endpoint (/apps/formbuilder/...)

Shopify signs these requests with an HMAC signature and passes the shop domain, so the backend can verify the request is legitimate and associate it with the correct shop

The App Proxy allows CORS from the Theme Editor iframe without needing to open a custom CORS policy on the backend
